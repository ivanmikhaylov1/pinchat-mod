# Выпуск релизов

[← README](../README.md) · [Тестирование](TESTING.md)

## Подготовка

1. Обновите `mod_version` в корневом `gradle.properties`, `fabric-mc26/gradle.properties` и `neoforge-mc26/gradle.properties`.
2. Если добавляется игра или загрузчик, обновите `config/targets.json` и соответствующую сборку. Матрица определяет тесты, названия JAR, таблицу совместимости и manifest.
3. Запустите unit-тесты, `./gradlew buildAll` и `python3 scripts/verify_loader_jars.py`.
4. Выполните `python3 scripts/release.py --tag v<mod_version>` и проверьте `dist/RELEASE_NOTES.md`. Скрипт отвергает несовпадающий тег, рассогласованные версии вложенных проектов, неверную версию в JAR и попавший в релиз тестовый код.
5. Проверьте игровой сценарий и визуальное качество. Список изменений для пользователей сохраняйте рядом с описаниями в `docs/releases`; не подменяйте его списком технических коммитов.
6. После ревью изменения можно отправить в основную ветку и создать тег `v<mod_version>` либо `<mod_version>`. Сам скрипт подготовки не отправляет теги и не публикует GitHub Release.

## Что получает игрок

- `pinchat-mod-<loader>-<version>-mc<minecraft>.jar`: явно названы мод, загрузчик и версия игры.
- Отдельные имена для 26.1.1 и 26.1.2, хотя байты совпадают с 26.1.
- `SHA256SUMS`: SHA-256 каждого из 16 файлов текущей матрицы.
- `manifest.json`: версия мода, версия Java/загрузчика/Fabric API, базовая версия бинарника, имя и SHA-256 файла.
- `GAMEPLAY_RESULTS.json`: результаты прогона всех сочетаний с SHA-256 проверенного JAR.
- Понятное описание: выбор файла, зависимости, установка, управление, проверки и ограничения.

Проверка загрузки всех JAR на Linux: `sha256sum --check SHA256SUMS`; на macOS: `shasum -a 256 --check SHA256SUMS`. Если скачан только один JAR, сравните его сумму с соответствующей строкой.

## Защита публикации

`build.yml` разделяет сборку, игровую матрицу и публикацию. Права записи в GitHub есть только у release-job. Он запускается по тегу после успешных build и gameplay jobs, проверяет суммы и сверяет полный набор JSON-отчётов с manifest. Отчёт от другого JAR не считается доказательством проверки текущего файла.

Теги с суффиксом (`v3.2.0-beta.1`) создают prerelease. Обычные теги выпускают стабильный релиз. Версия внутри JAR должна совпадать с тегом без начального `v`.

## Исторические релизы

Описания опубликованных релизов сохранены в `docs/releases`. Бинарники исторических версий не заменяются при редактировании оформления. Новые автотесты не приписываются старым версиям без отдельного прогона.

В метаданных 1.0.0 и 1.1.0 указано `~1.21.1` при исходном названии релиза 1.21.10. У 2.0.1 указан диапазон `1.21.11.x` вместо явного диапазона pre1–pre5; он отмечен как prerelease. Эти расхождения объяснены в описаниях, исходные JAR сохранены.
